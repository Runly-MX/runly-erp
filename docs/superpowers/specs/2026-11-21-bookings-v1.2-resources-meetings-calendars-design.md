# Reservaciones v1.2: resources, meetings and personal calendars

Status: R1 built and verified (2026-11-21, see the plan); R2 and R3 designed here, built only when asked.
Base: `docs/superpowers/specs/2026-11-18-bookings-engine-design.md` (engine rules, sections 4-7). Nothing here adds
a second availability engine, rebuilds Calendar or adds a video engine.

## 1. Goal

A company books its meeting room without overlaps (R1), runs a virtual session through Runly Chat/Llamadas (R2), and
the attendee adds the appointment to their personal calendar (R3). Three independent deliveries, each closed with a
versioned verification script.

## 2. Audit (working tree, 2026-11-21)

| Area | Finding |
|---|---|
| Engine | `booking.service_id` is required; appointments pick a resource among `eligibleResources` (space + service links, `capacity >= party`), `input.resourceId` pins one, staff may send `durationMinutes` (5-720), `sideEffect` writes an integration row in the same transaction. Exclusion constraint `booking_allocation_no_overlap` per resource (company-wide, so a room shared by two spaces never double-books). |
| Resources | `booking_resource` (company level, `type` includes `room`, `equipment`; `capacity` since POS phase). Schedules: space rules ∩ resource rules, exceptions. |
| Permissions | `bookings.access` is granted automatically by space membership (`syncAccessGrant`); module visibility needs it. |
| Calendar | `bookings-calendar.js` projects each booking into one calendar per space, shared with its members; Calendar only lists events of owned/shared calendars (attendees alone do not see them). | Calls | `NewMeetingDialog`, `call-links-service.js`, guest links, lobby: to be audited at the start of R2. |

## 3. R1: resource and room reservations

### Model (migration `20270111000000_bookings_resource_reservations`)

- `booking_space.purpose` `services` (default, today's behaviour) | `resources`. A resource space is a system for
  rooms/equipment: no commercial services, no portal pages.
- `booking_service.internal` boolean: a resource space owns exactly one internal service ("Reservación", appointment,
  no buffers, party 1..1000), created with the space, hidden from service lists and pickers, linked automatically to
  every resource of the space. Users never configure it. Partial unique index: one internal service per space.
- `booking.title` (motivo) and `booking.organizer_id` (user). Participants: `booking_participant` (booking, user;
  unique), written in the engine transaction through `sideEffect`.
- Policy (JSON, no migration): `reservers` `company` (anyone in the company with `bookings.reserve` or
  `bookings.access`) | `members` (only space members), `maxMinutes` (default 480). Existing `leadMinutes`,
  `horizonDays`, `requiresApproval`, `cancelUntilMinutes` keep their meaning.

### Rules

- A reservation is an engine booking on the internal service with `resourceId` pinned, `durationMinutes = end - start`
  (15-minute grid, 15..`maxMinutes`), `partySize = max(headcount, 1 + participants)`: the engine refuses a room too
  small (`NO_CAPACITY`), outside hours (`OUTSIDE_HOURS`) or taken (`23P01` → 409 `SLOT_TAKEN`). Two employees booking
  the same room at once: the exclusion constraint admits one.
- Organizer: the caller; space agents/admins may name another company user. Participants: company users (not bots).
- Cancel and move: the organizer, or space agents/admins; through `transitionTx`/`rescheduleTx` (same guarantees).
- Privacy in the agenda: title and participants are shown to the organizer, participants and space members; everybody
  else sees "Reservado" and the organizer's name.
- Permission `bookings.reserve` ("Reservar salas y recursos"): reservation routes accept it or `bookings.access`.

### Calendar

- Reserve from Calendar: a "Reservar sala" action in Calendar opens the same reservation dialog; the booking goes
  through the engine and the projection writes the calendar events (no dual write).
- Projection: besides the space calendar (members), a resource reservation is written into the default calendar of
  the organizer and of each participant (one event per calendar, reconciled by calendar id; title "Motivo · Sala",
  location = resource name). Deleting those events changes nothing in the engine (unchanged contract).

### API (`/bookings/rooms/*`)

`GET /bookings/rooms` (resource spaces I can reserve in, with resources), `GET /bookings/rooms/:spaceId/agenda?from&to`
(hours and busy blocks per resource), `POST /bookings/rooms/:spaceId/reservations` (Idempotency-Key),
`GET /bookings/rooms/mine`, `POST /bookings/rooms/reservations/:id/cancel|reschedule`. Space creation accepts
`purpose: 'resources'`; `PUT /bookings/spaces/:id/resources` keeps the internal service links in step.

### UI

"Reservar sala" screen in Reservaciones (`/rooms`): day timeline per resource (phone: one resource at a time with free
slots), tap a free slot → dialog (motivo, inicio, fin, participantes, personas; organizer editable for agents), "Mis
reservaciones" with cancel/move. Creating a system offers "Salas y recursos" vs "Servicios"; a resource system shows
only Recursos, Horario, Equipo and Reservaciones tabs.

## 4. R2: Runly Chat/Llamadas meetings (designed, not built)

- Service setting `meeting`: `none` | `runly` | `external` (URL, https only). Stored on `booking_service.meeting` JSON.
- `booking_meeting` (booking, kind, call link id or external URL, version) created by an adapter inside the confirm
  transaction (`sideEffect`), idempotent on `booking_id`; the call room is prepared (link + lobby) but never started.
  Reschedule updates the link window; cancel/reject revokes the link (no orphan rooms: the adapter owns the lifecycle,
  a worker sweep revokes links of terminal bookings).
- Guests join from the confirmation email and the manage page through a per-booking guest link (lobby on), never an
  internal link or company credentials. Audit of `NewMeetingDialog`, `call-links-service.js`, invitations, chat rooms
  and guest access is the first task of R2.

## 5. R3: personal calendars (designed, not built)

- "Agregar a Google Calendar", "Outlook" (template URLs) and "Descargar .ics" on the portal confirmation/manage page and
  in confirmation emails. `.ics` with stable `UID = booking-<id>@<instance host>`, `SEQUENCE` = booking version,
  `DTSTART;TZID=<IANA>` plus `VTIMEZONE`, `METHOD:REQUEST` for updates and `METHOD:CANCEL` (STATUS:CANCELLED) on
  cancellation, attached to the update/cancel emails.
- The `.ics` is served from a dedicated signed URL (HMAC of booking id + version, no manage token), so calendar
  services never receive the manage token.
- Limitation documented to the user: template links copy the event once; only the `.ics` attached to update emails
  updates calendars that honour iCalendar `SEQUENCE`.

## 6. Non-goals

Recurring reservations, multi-resource reservations (room + projector in one booking), free/busy from external
calendars, check-in for rooms.
